## One next real-decode discriminator — proposal only

The remaining high-value split is **whole-model device-stream/working-set cost
versus host/glue enqueue or inter-step pacing**, with physical padding/compile
mode checked first. Unchanged SASS does not eliminate allocator, code/data-cache,
TLB or clock effects at the full working set. No implementation/new GPU action
is authorised by this document.

Use the existing private worker hook, not a Torch operator profiler or RPC
framework. For one already-agreed old/new MTP-off64-token request/window:

1. Preallocate/prime a bounded timing-event ring and CPU scalar records during
   normal warmup, unarmed during compile/capture. Preserve weights, workload,
   prefix history and model/compile settings. Do not infer driver-event memory
   cost from handle count or install a new numerical admission guard.
2. Record a narrow compute-stream interval after input preparation and immediately
   before model execution, ending after normal LM-head `compute_logits` enqueue.
   `_model_forward()` alone **excludes the head** and cannot represent all model
   GPU work. Use CPU enqueue markers around replay/head and keep sampling/copy
   work outside the bracket explicit. An approved per-instance replay hook may
   additionally expose the graph span without a global class/model patch.
3. Save CPU-only logical request/step identity, actual unpadded/padded batch N,
   runtime FULL/piecewise mode, replay count and decode/prefill status. Do not
   synchronously inspect GPU tensors or infer padding from configured buckets.
4. No per-token sync, polling, `.item()`, event readback or logging. After the
   measured request only, wait once on the final event and export ring durations,
   CPU markers and the existing server/client interval counters. Overflow,
   missing head/stream coverage or shape mismatch is explicit—not a fallback.

Matching narrow spans with larger engine intervals moves the unexplained cost
outside the bracket (sampling/copy GPU, CPU/IPC/scheduler—not automatically CPU).
Longer spans with unchanged enqueue bounds move attention toward device-side
working-set/cache/allocator/clock effects, not automatically changed kernels.
Different padded N/replay mode identifies a different workload/compile path.
CUDA-event spans include dependencies and starvation if the host queues late;
they are **not kernel-busy unions**. Do not subtract CPU duration to invent pure
GPU compute. This one measurement partitions the hypotheses; it is not a new
telemetry framework or an end-to-end speedup proof.

## Precise specialisations to review, not implement automatically

The repeat preserves a small cost gap, but absolute exposure—not the relative
percentage—decides whether to develop a fix. Two tightly scoped diagnostics are:

- **BA/source addressing:** `nib_row_dot` in `core/include/bf16n/kernels.cuh`
  currently uses `load_x4(x+E,0)`, `E=512*c+128*j+4*lane`. A caller-specific
  constexpr address-mode parameter could compare the original `load_x4(x,E/4)`
  **only for scalar BF16/C4**, preserving the current default for GLU and FP32
  down. E is divisible by4, so no arithmetic or escape-load change is needed.
  Do not globally revert the shared helper and lose the measured shared-path
  gains. Inspect generated address scheduling/liveness, then judge latency and
  strict bits—not register count alone. BA-only recovery remains below the bar;
  a broader aggregate effect in other scalar shapes would need real evidence.
- **MC N2/launch-only diagnostic:** its original kernel uses `blockDim.x` for
  staging and warp/unit stride (`k_hp_mmv_mc`, lines618–683). A reviewed control
  could compare1024 threads ×SMs blocks with512 threads ×(2*SMs) blocks, keeping
  total warps/unit stride fixed and32KiB dynamic shared per CTA. Check actual
  register/shared residency first and require strict bits on both original
  cubins. More independent CTAs could test a scheduling/ILP explanation without
  recompiling a kernel. This is not a proposed strict-N1 fix: N2 reachability
  and aggregate exposure are still required, and extra LUT staging may lose.

Neither diagnostic nor a kernel/package change is performed here. The higher-value
next choice remains a real-decode span measurement or explicit tradeoff review,
not BA tuning simply because its relative percentage is large.

## Decision

Keep the shared-pair gains as observations, not a global speedup theorem. Retire
BA/MC repeat confounds with the already-authorised small experiment; do not spend
a kernel optimisation cycle on BA's relative percentage alone. Then either review
accepting the independently documented serving/native-PP tradeoffs, or authorise
the single matched real-decode event probe above if its answer can change the
choice. No merge/deployment, blanket waiver, full-model projection or automatic
GO follows; full-model verification remains required after any actual fix.
